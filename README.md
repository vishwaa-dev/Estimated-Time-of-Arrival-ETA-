RailCast AI

> **"Don't just predict arrival. Forecast the journey of the delay."**

RailCast AI is an **explainable, multi-factor, continuously re-calculated ETA intelligence
layer** that sits on top of existing train-tracking systems. Instead of the naive
`ETA = scheduled + current delay`, it forecasts how a delay will **propagate** across
upcoming stations, how much of it the train can plausibly **recover** through running-time
slack and dwell compression, and explains every factor behind the number.

---

## 1. Problem

Existing railway / passenger systems expose a train's **current status, current delay and
a basic ETA** (usually just `scheduled time + current delay`). They cannot answer the
questions that actually matter to a passenger at 2 AM:

- Will this +8 min delay **grow** before Madurai, or will the train make time up?
- Which sections will eat time, and where can the schedule breathe?
- When should I realistically expect the train — and how sure are you?

## 2. Solution

RailCast AI evaluates the current train state continuously and estimates:

1. Current delay
2. Predicted **additional** delay
3. **Recovery** potential (running slack + dwell compression, bounded)
4. Expected **final** delay
5. Estimated arrival time
6. **ETA range** (estimated interval)
7. **Confidence** (labelled *"Estimated confidence"*)
8. Major **factors/reasons** behind the prediction
9. **Station-by-station delay trajectory**
10. **Recovery feasibility map** per route section

Everything is presented with honest data-provenance badges: `LIVE`, `DEMO / SIMULATION`,
`SIMULATED`, `ESTIMATED`, `CACHED`, `MODEL`/`RULE-BASED`.

## 3. Architecture

```
Next.js frontend (poll-only)
        ↓  GET/POST /api/… (localhost:8000)
FastAPI backend  ──── RailRadar API  (live train state; TTL cache + hourly budget)
        │             OpenWeather API (weather at train location; TTL cache)
        ↓
SQLite  (trains, routes, state/weather/prediction snapshots, events, cache)
        ↑
Background scheduler (asyncio): LIVE trains re-fetch + re-forecast every
POLL_INTERVAL_SECONDS; the designated DEMO train advances its simulated
journey every DEMO_TICK_SECONDS; IDLE trains are left untouched
```

**The frontend never calls RailRadar or OpenWeather.** Only the backend spends external
API calls, guarded by in-memory + PostgreSQL caches, configurable TTLs and an hourly call
budget. The frontend polls the backend (which serves cached/database state for free).

### The core pipeline (unchanged, as mandated)

```
Train API → Current Train State → Route + Schedule → Weather → Feature Engineering
→ Delay Prediction → Recovery Estimation → Final ETA → Confidence / ETA Range
→ Explanation → Dashboard → (wait ≈5 min) → fetch new state → recalculate → refresh
```

## 5. Data sources

- **RailRadar** (`https://api.railradar.in/v1/trains/{number}/live`, Bearer token) — live
  train state, route, schedule, actuals. Key: `RAILRADAR_API_KEY` env var, never hardcoded.
- **OpenWeather** current weather at the train's interpolated position.
- **Provided snapshots** `data/train_12637.json` (Pandian SF Express) and
  `data/train_12168.json` (Mumbai LTT SF Express) are real single train-run snapshots —
  **not** historical bulk datasets. Eight more demo timetables (total 10 tracked trains)
  are generated by `scripts/add_trains_2026_10.py`.

## 6. RailRadar integration

`backend/app/services/railradar_service.py` is the only module that talks to RailRadar:

- In-memory TTL cache + persistent `api_cache` table (survives restarts)
- Sliding-window hourly call budget (`RAILRADAR_MAX_CALLS_PER_HOUR`)
- Explicit error mapping: timeout, 401/403 (bad key), 429 (rate limit), malformed JSON
- On failure the caller falls back to the **last successful snapshot** — the dashboard
  never goes blank, and the UI shows
  *"External data temporarily unavailable — showing last valid prediction."*

## 7. Weather integration

`weather_service.py` fetches current weather for the train's position (station registry
+ distance-weighted interpolation between known stations) and maps it to a **0–100 risk
score** (documented heuristic: condition family base + rainfall/wind/visibility bonuses,
banded NORMAL → VERY HIGH). Weather is a **risk input** only — the prototype never claims
"X mm rain causes Y min delay". DEMO mode uses clearly-labelled simulated weather presets.

## 8. Database schema

`trains`, `train_route_points`, `train_state_snapshots`, `weather_snapshots`,
`prediction_snapshots`, `prediction_factors` (see brief §7), plus `event_log` (timeline),
`api_cache` (external response cache) and `simulation_states` (DEMO scenario state).
**Snapshots are append-only** so every recalculation can compare current vs previous vs
scheduled state.

## 9. Prediction workflow

Centralised in `prediction_service.py` (no scattered formulas):

```
final_predicted_delay = current_delay + predicted_additional_delay − recovery_minutes
predicted_eta         = scheduled_eta + final_predicted_delay
```

`predict_additional_delay` components (each capped, sum clamped to [0, 60] min):

| Component | Rule |
|---|---|
| Speed | `dist_remaining × (1/current_speed − 1/expected_section_speed) × 60 × 0.6` when running below the scheduled profile |
| Stops | `upcoming_halts × 1.5 × dwell_factor` (dwell deviation + simulated congestion) |
| Weather | `(risk/100) × min(12, 2 + dist_remaining/60)` — risk heuristic |
| Trend | `clamp(0.5 × (current − previous), −2, +4)` — delay momentum |
| Time of day | `+1.5` inside peak windows (05–09, 17–21 IST) |
| Congestion | `6 × congestion_score` — simulated only, labelled |

Prediction hierarchy: **trained ML model → deterministic rule-based estimator**.
`prediction_method` in the API response always states which produced the number.

## 10. Recovery logic

Per remaining halt-to-halt section (see `recovery_service.py`):

- `slack = max(0, scheduled_running − distance/(avg_speed×1.15)×60)` — running margin
- `dwell_recovery = max(0, scheduled_dwell − 2 min) × 0.5` at intermediate halts
- Classification **HIGH / MEDIUM / LOW** by slack ratio (18% / 8% thresholds)
- Applied recovery is **bounded**: `min(total_recoverable, current_delay, MAX_RECOVERY_MINUTES)`
  — recovery can never exceed the delay it would erase.

## 11. ML approach

`app/ml/` generates **synthetic** training samples (perturbed operational states labelled
by a noisy copy of the rule estimator), trains `HistGradientBoostingRegressor`, and saves
the model. HONESTY: the model learns the prototype's own heuristics + noise — labelled
*"Prototype / synthetic training data"*. If the model file or scikit-learn is missing the
system silently falls back to the rule-based estimator. Train it with:

```bash
python scripts/manage.py train-model
```

## 12. Continuous recalculation

`refresh_service.py` implements `POST /api/trains/{n}/refresh` (full 12-step pipeline) and
an asyncio background scheduler: LIVE trains re-fetch + re-forecast every
`POLL_INTERVAL_SECONDS` (default 300); the designated DEMO train advances its simulated
journey every `DEMO_TICK_SECONDS` (default 45) and recalculates; IDLE trains are left
untouched until the user toggles LIVE or presses refresh. The frontend polls
`GET /api/trains/{n}/prediction` every 15 s — a self-contained recalculation with zero
external calls.

## 13. Simulation mode

Exactly one train — the designated demo train (`DEMO_TRAIN_NUMBER`, default **12637**) —
replays its seeded schedule on a virtual clock (`DEMO_TIME_SCALE=60` → 1 s real = 1 min
simulated, journey loops). Its simulated delay evolves with mean reversion and small
jitter, so forecasts keep changing naturally, and every simulated artifact is flagged
`SIMULATED`. A demo that never spends an API call, forever.

All other trains are **real-data only**: they show their last actual RailRadar snapshot
(honestly timestamped) until you flip their LIVE switch or press *Check live* — and
while idle they deliberately get **no forecast**: numbers are never invented from
stale data. With no API key configured, everything safely falls back to DEMO so a
fresh clone always works.

## 14. API endpoints

```
GET  /api/health
GET  /api/trains
GET  /api/trains/search?q=
GET  /api/trains/{train_number}
GET  /api/trains/{train_number}/state
GET  /api/trains/{train_number}/weather
GET  /api/trains/{train_number}/prediction
GET  /api/trains/{train_number}/events
POST /api/trains/{train_number}/live                   {enabled}
POST /api/trains/{train_number}/refresh
```

**Per-train live tracking (quota control):** every train has its own LIVE switch
(`POST …/live`, plus the `● LIVE ON / ○ GO LIVE` button on each card and the
`LIVE TRACKING: ON/OFF` button on each dashboard). Only switched-on trains are
refreshed from RailRadar by the scheduler; the designated demo train runs the free
DEMO simulation; everything else stays idle on real data. Trains that are not actively
running are polled 3× slower. The tracked trains are seeded from the
`data/train_*.json` snapshots on startup — there is deliberately no "add train" UI,
so the API surface stays minimal.

Interactive docs: `http://localhost:8000/docs`.

## 16–20. Installation & running

**One-click (Windows):** double-click **`start-railcast.bat`** — boots the backend
(:8000) and frontend (:3000) in their own windows and opens the dashboard.
**`stop-railcast.bat`** stops both.

**A. Zero-install dev mode (SQLite, demo + live-capable):**

```bash
# 1. Backend
cd backend
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
copy ..\.env.example ..\.env                         # fill in your keys
.venv\Scripts\uvicorn app.main:app --port 8000

# 2. Frontend (new terminal)
cd frontend
npm install
npm run dev            # http://localhost:3000
```

Startup automatically creates tables and seeds all tracked trains from the
`data/train_*.json` snapshots (works with zero API keys — everything runs the
DEMO replay; add real keys in `.env` and flip a train's LIVE switch for real
RailRadar data).

**Optional ML training:** `python scripts/manage.py train-model`
**Manual seed:** `python scripts/manage.py seed`
**Tests:** `cd backend && python -m pytest` (36 tests: parsing, delay/dwell/recovery/ETA
math, feature generation, weather risk, demo simulation engine, all API endpoints)

## 21. Prototype limitations

- **Multi-train network data is unavailable** through the initial RailRadar integration;
  a `network_context` object exists for future multi-train feeds.
- Operational events (signal faults, maintenance blocks) are simulated unless a real
  feed exists — the prototype never fabricates real railway incidents.
- The ML model is trained on **synthetic** data; no production accuracy is claimed.
- Weather influence is probabilistic, not deterministic.
- Confidence/ETA ranges are **estimated** heuristics, not statistically rigorous intervals.
- This is **not** a railway control system and must not drive operational decisions.
